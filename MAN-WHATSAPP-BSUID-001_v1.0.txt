1. VISÃO GERAL
--------------------------------------------------------------------------------

O WhatsApp passou a permitir nomes de usuário opcionais (ex.: @joaosilva).
Quando um usuário adota um nome de usuário, o número de telefone dele pode
deixar de aparecer nos webhooks enviados às empresas. Para que as empresas
continuem identificando e respondendo esses usuários, a Meta criou um novo
identificador de back-end: o BSUID — Business-Scoped User ID (ID do usuário no
escopo da empresa).

Em cinco linhas:
1. Nomes de usuário são opcionais para pessoas e empresas.
2. Quando adotados por um usuário, o telefone pode ser omitido dos webhooks.
3. O BSUID identifica o usuário de forma única DENTRO de um portfólio empresarial.
4. O suporte a BSUID é OBRIGATÓRIO para parceiros, empresas integradas
   diretamente na Plataforma do WhatsApp Business e anunciantes de CTWA.
5. Quem não migrar pode PERDER a capacidade de processar mensagens — não há
   correção retroativa.

Escopo: entender o BSUID, onde ele aparece, como enviar mensagens para ele,
como recuperar o telefone do usuário e o que fazer para migrar integrações.
Fora do escopo: detalhes internos da Meta, preços, políticas não documentadas.

2. MAPA DO SISTEMA
--------------------------------------------------------------------------------

Usuário do WhatsApp
   |  (pode ou não adotar @username)
   v
Plataforma do WhatsApp Business (Meta)
   |
   +-- Webhooks ------------> Sua integração (CRM, bot, n8n, backend)
   |    - messages (recebidas, status)
   |    - contacts
   |    - system (troca de número/BSUID)
   |    - user_preferences
   |    - history / smb_message_echoes / smb_app_state_sync
   |    - groups / group_participants_update
   |    - calls (API de Ligações / SIP)
   |    - business_username_updates
   |
   +-- APIs ----------------> Sua integração envia mensagens/ligações
   |    - Messages API (to | recipient)
   |    - Marketing Messages API
   |    - Groups API
   |    - Block Users API
   |    - Calls API (SIP)
   |    - Username API
   |    - Contact Book API
   |    - Parent BSUID Accounts API
   |
   +-- Contact Book (hospedado pela Meta)
        - Armazena telefone + BSUID após interação
        - Preenche webhooks com o telefone quando disponível

Fluxo de identificação de um usuário:

Mensagem recebida
   |
   +-- user_id / from_user_id      -> SEMPRE presente (BSUID)
   +-- parent_user_id              -> se BSUID principal habilitado
   +-- username                    -> se o usuário adotou nome de usuário
   +-- wa_id / from / recipient_id -> SÓ se o telefone estiver disponível
                                      (cache de 30 dias OU Contact Book)

3. GLOSSÁRIO
--------------------------------------------------------------------------------

BSUID
  Business-Scoped User ID. Identificador único de um usuário do WhatsApp,
  vinculado a um portfólio empresarial específico. Formato:
  US.13491208655302741918 (código ISO 3166 alfa-2 + ponto + até 128
  caracteres alfanuméricos).

BSUID principal / Parent BSUID
  BSUID compartilhado entre portfólios empresariais inscritos na mesma conta
  principal. Formato com ENT: US.ENT.11815799212886844830. Requer inscrição
  junto ao contato da Meta.

Portfólio empresarial
  Antigo "Gerenciador de Negócios" (Business Manager). Os BSUIDs são
  associados a portfólios individuais.

Nome de usuário (username)
  Nome único e opcional que o usuário define para exibir no app em vez do
  número de telefone.

Nome de usuário comercial
  Nome de usuário adotado por uma empresa. NÃO oculta o telefone comercial
  no app.

Contact Book (Lista de Contatos)
  Recurso hospedado pela Meta que armazena telefone + BSUID de usuários após
  interação. Preenche webhooks com o telefone.

REQUEST_CONTACT_INFO
  Novo tipo de botão (em templates utility/marketing ou mensagem interativa)
  que solicita ao usuário o compartilhamento do telefone.

CTWA
  Click-to-WhatsApp Ads — anúncios que levam o usuário diretamente ao
  WhatsApp.

Webhook
  Chamada HTTP enviada pela Meta à sua integração quando ocorre um evento
  (mensagem recebida, status, etc.).

wa_id
  Campo de webhook que historicamente continha o número de telefone do
  usuário. Agora PODE SER OMITIDO.

user_id
  Novo campo de webhook que contém o BSUID. SEMPRE PRESENTE.

parent_user_id
  Campo de webhook que contém o BSUID principal, quando habilitado.

Cache de 30 dias
  Janela em que o telefone do usuário continua sendo incluído em webhooks se
  houve interação recente (avaliada POR NÚMERO COMERCIAL).

SIP
  Session Initiation Protocol — protocolo usado pela API de Ligações.

4. MÓDULOS / COMPONENTES
--------------------------------------------------------------------------------

4.1 MÓDULO: NOMES DE USUÁRIO (USUÁRIO FINAL)

Função:    permitir que usuários do WhatsApp exibam um nome único em vez do
           telefone.
Motivo:    privacidade e personalização.
Entradas:  username definido pelo usuário no app.
Processo:  a Meta passa a incluí-lo no campo username dos webhooks.
Saídas:    webhooks com username presente; telefone pode ser omitido.
Riscos:    integrações que assumem wa_id sempre presente quebram.

Original (SRC-001):
  "O nome de usuário é um nome único e opcional que os usuários do WhatsApp
   podem definir para exibir no app em vez do número de telefone. Em vez dos
   nomes de perfil, é possível usar os nomes de usuário para personalizar o
   conteúdo de mensagens para usuários individuais."

  "Os usuários do WhatsApp podem ter apenas um nome de usuário, mas é
   possível alterá-lo periodicamente. A alteração do nome de usuário não
   afeta o número de telefone nem o ID do usuário no escopo da empresa."

4.2 MÓDULO: BSUID (BUSINESS-SCOPED USER ID)

Função:    identificar unicamente um usuário do WhatsApp dentro de um
           portfólio empresarial.
Motivo:    permitir envio e recebimento de mensagens mesmo sem o telefone.
Entradas:  gerado automaticamente pela Meta.
Processo:  atribuído ao campo user_id em todos os webhooks de mensagens.
Saídas:    envio de mensagens via recipient; identificação de usuários sem
           telefone.
Riscos:
  - BSUID é único por par usuário + portfólio; enviar de outro portfólio falha.
  - BSUID é regerado quando o usuário troca de número (dispara webhook de
    sistema).
  - BSUIDs NÃO podem ser usados em templates de autenticação de um toque,
    sem toque e de copiar código (exigem telefone).

Original (SRC-001):
  "Um BSUID é um identificador de usuário único que pode ser usado para
   enviar mensagens a um usuário do WhatsApp quando você não sabe o número
   de telefone dele. O BSUID será atribuído ao parâmetro user_id e aparecerá
   em todos os webhooks de mensagens, independentemente de o usuário ter
   habilitado ou não o recurso de nome de usuário."

  "Os BSUIDs são associados a portfólios empresariais individuais. Isso
   significa que qualquer número de telefone comercial de um determinado
   portfólio pode ser usado para enviar mensagens a um BSUID no mesmo
   portfólio. As tentativas de enviar mensagens ao BSUID usando um número de
   telefone de um portfólio diferente não terão sucesso."

Características (Original, SRC-001):
  "Os BSUIDs serão:
   - gerados automaticamente
   - prefixados com o código do país ISO 3166 alfa-2 de duas letras do
     usuário e um ponto, seguido de até 128 caracteres alfanuméricos (por
     exemplo, US.13491208655302741918)
   - únicos para cada par de usuário e portfólio empresarial (antes chamados
     de Gerenciadores de Negócios)
   - gerados novamente se um usuário mudar o número de telefone (o que
     dispara um webhook de mensagens do sistema)"

4.3 MÓDULO: BSUID PRINCIPAL (PARENT BSUID)

Função:    permitir que um mesmo usuário seja identificado por um único BSUID
           em VÁRIOS portfólios de uma empresa gerenciada.
Motivo:    empresas com múltiplos portfólios precisam de identidade unificada.
Pré-req.:  pedir ao ponto de contato da Meta para verificar se a organização
           se qualifica e inscrever os portfólios.
Entradas:  inscrição aprovada pela Meta.
Processo:  Meta inclui parent_user_id em todos os webhooks.
Saídas:    envio via recipient com BSUID principal; webhooks com
           parent_user_id e parent_recipient_user_id / from_parent_user_id.
Riscos:
  - NÃO é suportado em bloqueio/desbloqueio de usuários (a solicitação falha).
  - NÃO é suportado na Contact Book (a solicitação falha com erro, em vez de
    retornar present: false).
  - Requer inscrição; não é automático.

Original (SRC-001):
  "Caso seja uma empresa gerenciada e queira inscrever seus portfólios
   empresariais para receber BSUIDs principais, você pode pedir ao seu ponto
   de contato da Meta para verificar se a organização se qualifica. Se você
   se qualificar e os portfólios empresariais forem inscritos, os BSUIDs
   principais serão incluídos em todos os webhooks de mensagens, atribuídos
   a uma nova propriedade parent_user_id."

  "Os BSUIDs principais seguem o mesmo formato dos BSUIDs normais, mas
   incluem ENT entre o código do país e o identificador alfanumérico (por
   exemplo, US.ENT.11815799212886844830)."

4.4 MÓDULO: CONTACT BOOK (LISTA DE CONTATOS)

Função:    armazenar telefone + BSUID de usuários que interagiram com a
           empresa, para preencher webhooks com o telefone.
Motivo:    reduzir a perda de contexto quando o usuário adota nome de
           usuário.
Entradas:  interações (mensagem/ligação) após o lançamento do recurso;
           botão REQUEST_CONTACT_INFO.
Processo:  a Meta armazena automaticamente; não requer integração.
Saídas:    webhooks passam a incluir o telefone novamente.
Riscos:
  - Escopo POR PORTFÓLIO; não sincroniza entre portfólios inscritos no mesmo
    BSUID principal.
  - Interações ANTERIORES ao lançamento NÃO são capturadas retroativamente.
  - Desativar o recurso APAGA os dados já salvos; reativar não restaura.
  - Só preenche cargas de webhook, não respostas de API.

Original (SRC-001):
  "Para auxiliar na continuidade das conversas, oferecemos um recurso de
   lista de contatos que armazena informações de contato de usuários do
   WhatsApp. O livro de contatos é fornecido e hospedado pela Meta. Não é
   necessária nenhuma integração."

  "Os dados da lista de contatos serão mantidos até você desabilitar o
   recurso ou desativar a conta. Se desejar, você poderá desabilitar esse
   recurso no painel Meta Business Suite > Configurações da empresa >
   Informações da empresa."

Limitação (Original, SRC-001):
  "As listas de contatos são associadas aos portfólios empresariais. Isso
   significa que, se você tiver vários portfólios inscritos na mesma conta
   do BSUID principal, o número de telefone e o BSUID de um usuário terão
   que ser registrados no livro de contatos de cada portfólio de forma
   independente, já que as informações de contato do usuário não são
   compartilhadas ou sincronizadas entre portfólios inscritos."

4.5 MÓDULO: BOTÃO REQUEST_CONTACT_INFO

Função:    solicitar ao usuário que compartilhe o próprio telefone.
Motivo:    obter o telefone quando ele não está disponível nos webhooks.
Entradas:  template utility/marketing com botão REQUEST_CONTACT_INFO OU
           mensagem interativa request_contact_info.
Processo:  usuário toca no botão; dispara webhook contacts.
Saídas:    webhook com phones[].phone, origin: contact_request; se o usuário
           compartilhar contato manualmente, origin: other e vcard.
Riscos:
  - O rótulo do botão NÃO pode ser personalizado.
  - Se o usuário NÃO compartilhar o telefone, é preciso tratar esse cenário.

Original (SRC-001):
  "Para facilitar a solicitação de números de telefone de usuários do
   WhatsApp, está disponível um novo tipo de botão REQUEST_CONTACT_INFO que
   pode ser incluído nos modelos utility e marketing ou enviado como uma
   mensagem interativa."

  "Os botões de pedido de informações de contato não podem ser
   personalizados. Portanto, não é preciso incluir valores de parâmetro ao
   enviar o modelo"

4.6 MÓDULO: NOMES DE USUÁRIO COMERCIAIS (EMPRESA)

Função:    permitir que a empresa adote um nome de usuário pesquisável.
Motivo:    identificador único e pesquisável; usuários finais não podem
           pesquisar por nome de exibição.
Entradas:  username desejado; opcionalmente transfer_action
           (none | force_transfer).
Processo:  POST na Username API; aprovação da Meta.
Saídas:    status: approved ou reserved.
Riscos:
  - Formato restrito: 3–35 caracteres; apenas a-z, 0-9, . e _; sem acentos;
    não começar/terminar com ponto; não começar com www.; não terminar com
    domínio.
  - Um username = um número comercial; único no WhatsApp inteiro.
  - Se o username já é usado na Página do Facebook ou conta do Instagram, é
    preciso vincular o telefone à Página/Conta.
  - NÃO oculta o telefone comercial no app.

Original (SRC-001):
  "As empresas também poderão adotar um nome de usuário comercial. No
   entanto, se você adotar um nome de usuário comercial, o número de
   telefone da empresa não ficará oculto no cliente do WhatsApp ou do
   WhatsApp Business."

  "Cada nome de usuário comercial é mapeado para um único número de telefone
   comercial em todo o WhatsApp. Ou seja, um número de telefone pode ter
   apenas um nome de usuário por vez."

Prioridade de exibição (Original, SRC-001):
  "A prioridade a seguir será observada (em ordem decrescente de prioridade)
   para a exibição de informações do perfil comercial nas janelas de
   conversa no app. Os números de telefone comerciais sempre aparecerão no
   seu perfil empresarial.
   1. Nome salvo do contato
   2. Nome comercial verificado ou nome da conta comercial oficial
   3. Nome de usuário
   4. Número de telefone"

4.7 MÓDULO: WEBHOOKS DE SISTEMA (TROCA DE NÚMERO/BSUID)

Função:    notificar a integração quando o usuário troca de número ou quando
           o BSUID muda.
Motivo:    manter o vínculo entre a identidade antiga e a nova no CRM.
Entradas:  ação do usuário no app.
Processo:  webhook messages com type: system.
Saídas:
  - system.type = user_changed_number — quando o novo telefone pode ser
    compartilhado; contém previous_user_id e previous_parent_user_id.
  - system.type = user_changed_user_id — quando só a mudança de BSUID pode
    ser relatada; wa_id é omitido.
Riscos:    não existe campo de webhook user_id_update assinável; a mudança
           chega em messages como system.

Original (SRC-001):
  "Adição de um novo gatilho: agora um webhook de mensagens do sistema será
   disparado quando um usuário do WhatsApp alterar o número de telefone
   usando o app para consumidores."

  "Não existe um campo de webhook user_id_update. As alterações de BSUID são
   entregues no campo messages como uma mensagem do sistema."

4.8 MÓDULO: WEBHOOK BUSINESS_USERNAME_UPDATES

Função:    notificar mudanças de status do nome de usuário comercial.
Motivo:    acompanhar aprovação, reserva, exclusão e revogação.
Entradas:  mudança de status na Meta.
Processo:  webhook no campo business_username_updates.
Saídas:    status (approved | deleted | reserved) e context (revoked, quando
           aplicável).
Riscos:    context ausente não identifica quem iniciou a mudança.

Original (SRC-001):
  "Um novo webhook business_username_updates será adicionado. Esse webhook
   será disparado quando o status do nome de usuário de uma empresa for
   alterado."

  "context – Contexto adicional sobre o motivo pelo qual o nome de usuário
   atingiu o estado denunciado por status. É exibido apenas quando há algo
   para informar além do próprio status. No momento, revoked é o único
   valor."

5.1 PROC-001 — ENTENDER ONDE O BSUID APARECE

Objetivo:  saber em quais campos de webhook e API o BSUID é retornado.
Uso:       planejamento de integração e ajuste de parsers.
Pré-req.:  acesso à documentação e ao Painel de Apps.
Entradas:  documentação (SRC-001).
Passos:
  1. Em mensagens recebidas, procure contacts[].user_id e
     messages[].from_user_id. Sempre presentes.
  2. Em status de mensagens de saída (sent/delivered/read), procure
     contacts[].user_id e statuses[].recipient_user_id. Sempre presentes.
  3. Em status failed, contacts é omitido e recipient_user_id é omitido se a
     mensagem foi enviada ao telefone.
  4. Em contatos (compartilhamento), procure contacts[].user_id e
     messages[].from_user_id.
  5. Em mensagens do sistema, procure system.user_id,
     system.previous_user_id, system.parent_user_id,
     system.previous_parent_user_id.
  6. Em grupos, procure participants[].user_id,
     recipient_participant_user_id, from_user_id, from_parent_user_id.
  7. Em ligações, procure from_user_id / to_user_id / recipient_user_id e
     variantes parent.
  8. Em respostas de envio, procure contacts[].user_id (omitido quando o
     envio foi por telefone).
Saída:     mapa de campos por tipo de webhook.
Validação: comparar com as tabelas de referência rápida da Seção 6.
Falhas:    assumir que wa_id sempre existe.
Riscos:    parsers antigos quebram ao receber payload sem telefone.
Fontes:    SRC-001 (seções "Referência rápida sobre identificadores de
           webhook", "Webhooks de mensagens", "API de Grupos",
           "API de Ligações").
Estado:    documentado; não testado.

Original (SRC-001, tabela de webhooks de mensagens recebidas):

5.2 PROC-002 — ENVIAR MENSAGEM USANDO BSUID

Objetivo:  enviar mensagem a um usuário sem saber o telefone.
Uso:       quando o webhook trouxe apenas user_id.
Pré-req.:  API compatível com BSUID (a partir de julho de 2026); BSUID do
           mesmo portfólio do número comercial remetente.
Entradas:  recipient (BSUID ou BSUID principal) OU to (telefone), nunca
           ambos com intenção de usar o BSUID (telefone tem precedência).
Passos:
  1. Monte a requisição para POST
     https://graph.facebook.com/<API_VERSION>/<BUSINESS_PHONE_NUMBER_ID>/messages
  2. Inclua "messaging_product": "whatsapp" e
     "recipient_type": "individual".
  3. Para enviar SÓ COM BSUID: defina "recipient": "<BSUID>" e OMITA to.
  4. Para enviar SÓ COM TELEFONE: defina "to": "<PHONE>" e OMITA recipient.
  5. Para enviar COM AMBOS: defina os dois; o telefone tem precedência.
  6. Verifique a resposta: se enviado por BSUID, contacts[].input e
     contacts[].user_id retornam o BSUID e wa_id é omitido.
Saída:     mensagem aceita pela API.
Validação: resposta HTTP 200 com messages[].id; contacts[].user_id presente
           quando envio por BSUID.
Falhas:
  - Código 131062 — Business-scoped User ID (BSUID) recipients are not
    supported for this message.
  - Templates de autenticação (um toque, sem toque, copiar código) NÃO
    aceitam BSUID.
  - BSUID de outro portfólio falha.
Riscos:    enviar to e recipient achando que o BSUID será usado — o telefone
           vence.
Fontes:    SRC-001 (seções "Como enviar pedidos de contato", "Como enviar
           solicitações de mensagem de marketing", "Códigos de erro").
Estado:    documentado; não testado.

Original (SRC-001):
  {
    "messaging_product": "whatsapp",
    "recipient_type": "individual",
    "to": "<USER_PHONE_NUMBER>",
    "recipient": "<BSUID>",
    "type": "text",
    "text": {
      "body": "<BODY_TEXT>"
    }
  }

Original (SRC-001, resposta ao enviar para BSUID):
  {
    "messaging_product": "whatsapp",
    "contacts": [
      {
        "input": "US.13491208655302741918",
        "user_id": "US.13491208655302741918"
      }
    ],
    "messages": [
      {
        "id": "wamid.HBgLMTY0NjcwNDM1OTUVAgARGBI1RjQyNUE3NEYxMzAzMzQ5MkEA"
      }
    ]

5.3 PROC-003 — RECUPERAR O TELEFONE DO USUÁRIO NOS WEBHOOKS

Objetivo:  fazer o telefone voltar a aparecer nos webhooks quando o usuário
           adotou nome de usuário.
Uso:       manter o contexto da conversa no CRM.
Pré-req.:  Contact Book ativado (Meta Business Suite > Configurações da
           empresa > Informações da empresa).
Entradas:  interação recente ou entrada no Contact Book.
Passos:
  1. Verifique se o Contact Book está ativado.
  2. Garanta que houve interação (mensagem/ligação) APÓS o lançamento do

     o telefone.
  5. Se present: false, solicite o telefone via botão REQUEST_CONTACT_INFO

Validação: resposta com present: true.

Fontes:    SRC-001 (seções "Números de telefone", "Lista de contatos",

Estado:    documentado; não testado.

DEC-001 — Usar BSUID como chave primária de usuário, telefone como campo extra
  Motivo: o telefone pode ser omitido dos webhooks; o BSUID é sempre presente.
  Alternativas consideradas: manter telefone como chave e tratar BSUID como
    campo adicional.
  Evidências: SRC-001 (tabelas de referência rápida); SRC-002 ("Nunca mais
    use telefone como ID único. Use user_id (BSUID). Telefone é só um campo
    extra que pode estar ou não.").
  Data: 23 de out. de 2026.
  Estado: recomendação; não implementada/testada.

DEC-002 — Ativar o Contact Book
  Motivo: é o mecanismo que faz o telefone voltar aos webhooks.
  Alternativas consideradas: depender apenas do cache de 30 dias; solicitar
    telefone manualmente.
  Evidências: SRC-001 (seção "Lista de contatos"); SRC-002.
  Data: 23 de out. de 2026.
  Estado: recomendação; não implementada/testada.

DEC-003 — Implementar REQUEST_CONTACT_INFO na jornada
  Motivo: obter o telefone quando o usuário não o compartilha
    espontaneamente.
  Alternativas consideradas: não solicitar e operar só com BSUID.
  Evidências: SRC-001 (seção "Como solicitar o número de telefone dos
    usuários"); SRC-002.
  Data: 23 de out. de 2026.
  Estado: recomendação; não implementada/testada.

  Início de abril/2026  | BSUIDs começam a chegar nos webhooks (user_id)

7.3 REGRAS DE FORMATO — USERNAME COMERCIAL (Original, SRC-001)

  "Os nomes de usuário comerciais devem ter o seguinte formato:
   - podem conter apenas letras do alfabeto inglês (a-z), dígitos (0-9),
     ponto (.) e caracteres de sublinhado (_)
   - caracteres que não são letras do alfabeto inglês (como ñ, é, ü) não
     são compatíveis e causarão falhas na solicitação
   - devem ter entre 3 e 35 caracteres
   - devem conter pelo menos uma letra do alfabeto inglês (a-z, A-Z)
   - não podem começar nem terminar com ponto nem ter dois pontos
     consecutivos
   - não devem começar com www.
   - não devem terminar com um domínio (por exemplo, .com, .org, .net,
     .int, .edu, .gov, .mil, .arpa, .html, .htm, .txt, .xml).
   - a diferença entre maiúsculas e minúsculas é ignorada ao comparar nomes
     de usuário, mas os caracteres de ponto e sublinhado não."

9. LACUNAS E CONFLITOS
--------------------------------------------------------------------------------

LAC-001 — Stack da integração não informada
  Dado faltante: linguagem/framework e provedor (webhook próprio vs.
    Twilio/360Dialog/Gupshup).
  Impacto: impossível indicar o trecho exato de código a alterar.
  Como obter: perguntar ao responsável (Pergunta 1 na Seção 12).

LAC-002 — Contact Book não confirmado como ativado
  Dado faltante: status atual do recurso na conta.
  Impacto: sem ele, o telefone pode não voltar aos webhooks.
  Como obter: verificar em Meta Business Suite > Configurações da empresa >
    Informações da empresa.

LAC-003 — BSUID principal não confirmado
  Dado faltante: se a empresa é gerenciada com múltiplos portfólios e se foi
    inscrita.
  Impacto: define se parent_user_id aparecerá nos webhooks.
  Como obter: consultar o ponto de contato da Meta; usar PROC-010.

LAC-004 — Sem testes práticos registrados
  Dado faltante: resultados reais de envio/recebimento com BSUID.
  Impacto: todos os procedimentos estão "documentados; não testados".
  Como obter: executar PROC-007 no Painel de Apps e registrar resultados.

LAC-005 — Detalhes de grupos e ligações não aprofundados
  Dado faltante: exemplos completos de webhooks de grupos e SIP além dos
    trechos da fonte.
  Impacto: cobertura parcial para quem usa Groups API ou Calls API.
  Como obter: consultar a documentação oficial específica.

CON-001 — Datas de disponibilidade divergentes entre versões do documento
  Conflito: a fonte registra mudanças de data ao longo do changelog (ex.:
    envio para BSUID previsto para maio/2026, depois julho/2026;
    REQUEST_CONTACT_INFO previsto para maio/2026, depois julho/2026; webhook
    BSUID de 31 de março para início de abril/2026).
  Alternativas preservadas: usar as datas mais recentes do changelog
    (julho/2026 para envio; início de julho/2026 para o botão; início de
    abril/2026 para webhooks).
  Estado: resolvido a favor da versão mais recente; datas antigas
    preservadas no histórico (Seção 11).

CON-002 — "Tráfego direto" vs. "resposta direta"
  Conflito aparente: SRC-003 distingue os dois conceitos; não há conflito
    técnico com BSUID.
  Estado: esclarecido na fonte; registrado para evitar confusão futura.

CON-003 — Duplicidade de fontes do documento Meta
  Conflito: o mesmo documento foi fornecido em dois arquivos
    ("analisa esse documento aqui.txt" e "Título da conversa.txt").
  Alternativas preservadas: tratados como SRC-001 (conteúdo idêntico).
    Possível duplicidade registrada; nenhum conteúdo perdido.
